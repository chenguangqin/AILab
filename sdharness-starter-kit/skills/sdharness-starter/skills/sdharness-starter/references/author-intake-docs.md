# Authoring intake docs — `vision.md` + `tech-env.md` (concierge guide)

Goal: help someone write an **intent bundle** the SD Loop can drive to a great result. The single
biggest lever on output quality is input quality — the run is autonomous, so there's no mid-flight
course-correction. Get the intake right and the loop does the rest.

Use this when a user wants to point the loop at their own use case (Level 300, Path A). The kit ships
fill-in templates at `agent-context/templates/{vision,tech-env}.md`; this guide is how to fill them well.

---

## The mental model: two files, two jobs

- **`vision.md` — the WHAT and WHY.** The intent: the problem, the user, the one feature, and a
  concrete **"Done ="**. Keep the *direction* **lean** — say what and why; do **not** hand-author the
  solution, a file layout, or a section-by-section UI spec. Let RESEARCH and PLAN own the *how*.
- **`tech-env.md` — the HOW-constraints (optional but powerful).** The **authoritative** layer: it
  *wins* over any stack the agent would otherwise free-choose. Keep the *resources* **rich** — pin the
  stack, list prohibitions, and give the **validation commands** that become the VERIFY seam.

The rule of thumb: **every sentence should either state intent or remove a failure mode.** Delete
anything that's just you doing the loop's planning for it. (Full philosophy:
`docs/concepts/loop-engineering.md` → "Setting the loop up for success".)

**What you do NOT author:** `goal.md` and `design.md` are **generated by the loop in PLAN**, grounded
in its own RESEARCH — not hand-written. (You *may* drop a `goal.md` in the intake and the loop will use
it, but the default and the norm is to let PLAN write it.)

---

## Interview first, then draft (how to help a user)

Don't hand a user a blank template. Walk them through six questions, one batch at a time, then draft the
files and reflect back before running:

1. **Problem** — what specific pain, for whom? What's the workaround today?
2. **Primary user + the ONE feature** — the single buildable slice that proves the core value (not the
   whole platform).
3. **Definition of done** — *"how would you check it's actually done right?"* Push for something
   **verifiable**, not "it works" (see below — this is the most important answer).
4. **Scope & non-goals** — what it deliberately does *not* do. Non-goals are the single best defense
   against a sprawling run.
5. **Hard constraints** — stack, must-not-use, target environment (→ `tech-env.md`).
6. **Concrete anchors** — any "make it like X" reference, example, or provided asset (images, CSVs).

Then **reflect back** a one-paragraph summary + the proposed non-goals and ask *"did I get this right?"*
Cheap course-correction beats a wasted multi-turn run.

## `vision.md` — section by section

Follow `agent-context/templates/vision.md`. Universal sections: a title + lead paragraph, **Problem &
Users**, **What we're building (the ONE feature)**, **Expected outcomes** (as *user action → system
response*), **Done =**, **Scope** (In / Out-deferred), **Success bar & non-negotiables**, **Open
questions**. (`examples/mini-factory/vision.md` is the canonical structure; `bake-like-a-pro` is a leaner
frontend-showcase variant.)

### The "Done =" is the heart of it
It must be **observable end-to-end behavior, not "code exists"** — the loop proves it in VERIFY, so it
should read like something a check could assert. Two worked examples that hit the bar:

> *(bake-like-a-pro)* "`npm run build` succeeds, the site runs locally, and a scripted check confirms
> the course title, the 5 module names, the 3 prices ($29 / $89 / $19), and the enroll confirmation are
> present … **How you get there is yours to plan.**"

> *(mini-factory)* "…proven by an automated check that: (1) POSTing a launch returns a run id; (2) the
> run's events stream to the browser and render as turns/phases; (3) on completion the result (status +
> cost + milestones) is shown and the registry lists it. The check must pass **fast and cheaply** —
> against a fixture — never a full ~20-minute build."

Note the pattern: concrete, checkable assertions + the loop-engineering refrain **"how you get there is
yours to plan"** (that's the lean-direction discipline in one line).

### For a UI/frontend intent
Set the **craft bar as directional art-direction**, not a pixel spec: name the vibe/identity and the
must-haves, ask for the `frontend-design` skill, and let PLAN settle the tokens into `loop-docs/design.md`.
`examples/mini-factory/vision.md` (the "Lights-Out Factory Floor" identity) shows the level: bold
direction + guardrails ("color = meaning", responsive at 375/768/1440), not CSS.

## `tech-env.md` — section by section

Follow `agent-context/templates/tech-env.md`. Sections: a **Summary** table (Project type / Language /
Package manager / Deploy target), **Frameworks & services** (per-layer stack picks — label them
"directional" so the loop can refine), **Prohibitions**, and **Validation commands**.

- **Validation commands ARE the definition of done, made runnable.** Whatever you put here, the agent
  runs — and it becomes the VERIFY seam. Prefer a fast/cheap seam (a fixture, a `pytest -q`, a `curl` to
  a local endpoint) over anything that needs a 20-minute real run.
- **Prohibitions remove failure modes.** Pin what the agent must not use or do — the strongest lever
  when the agent keeps drifting to the wrong stack.

### Prohibitions worth defaulting to (learned the hard way)
- **No fabricated data anywhere it faces the user** — a stand-in/fixture must mirror the real thing (the
  kit ships exactly one method, `loop`; don't let a fixture invent a method catalog).
- **No private/auth-gated links in shipped UI or docs** — the output may run offline for a stranger; a
  dead internal link reads as broken. And keep shipped docs free of environment-internal identifiers.
- **User-facing microcopy is plain, not internal jargon** — labels/hints must make sense to someone who
  never saw the run's design docs.
- **No leftover stubs / TODOs / lorem-ipsum** in shipped code.

## Supporting resources (rich is good here)

Any other `*.md` (or CSV, etc.) you drop in the intake dir is staged to the workspace root as a
supporting input — this is where "rich resources" lives: `images.md` (license-free asset URLs),
content CSVs, an API sketch. Provide the *assets and facts* the loop needs; don't provide its plan.

---

## Checklist before you run

- [ ] `vision.md` has a concrete, **verifiable "Done ="** (a check could assert it) ending with
      "how you get there is yours to plan."
- [ ] The ONE feature is a single buildable slice, not a platform.
- [ ] **Non-goals** are stated (Scope → Out).
- [ ] Direction is **lean** — no hand-authored file layout / section-by-section UI spec.
- [ ] `tech-env.md` pins the stack + prohibitions + **validation commands** (the VERIFY seam).
- [ ] Resources are rich (assets/constraints/anchors provided).
- [ ] No `goal.md`/`design.md` hand-written (the loop generates them) — unless deliberately seeding.
- [ ] No fabricated data, no private/auth-gated links, no internal identifiers, plain microcopy.
- [ ] Reflected the summary + non-goals back to the user and got a "yes".

## Common pitfalls
- **Prescriptive instead of directional** — writing the loop's plan for it (file lists, exact
  components). Say what/why; delete the how.
- **Vague "Done ="** — "it works" / "a nice UI". Not checkable → the loop can't prove it and you can't
  trust it. Push for observable behavior.
- **No non-goals** — the run sprawls. Bound it.
- **Over-stuffed direction, thin resources** — the opposite of the rule. Trim the essay; add the assets,
  constraints, and validation commands.
- **Assuming the whole product** — scope to the Phase-1 slice that proves the value.
